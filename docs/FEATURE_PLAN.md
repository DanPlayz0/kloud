# Kloud feature plan

Updated November 1, 2026. This document defines the agreed Kloud feature scope, implementation milestones, acceptance criteria, and deferred backlog. Current-state observations come from the local working tree and are not a live deployment audit.

## Confirmed product direction

This section records the agreed product requirements. The feature inventory below is a broader backlog; the revised deployment release plan defines first-release scope.

- Audience: the owner and a small team, operating five servers. Teammates manage assigned apps; administrators manage hosts and shared settings.
- Immediate goal: easier application deployments, with PostgreSQL recovery and both variable editors explicitly included in the same first release. Expanded monitoring and templates remain deferred.
- Workloads: Docker Compose APIs (Go, TypeScript, Hono, Express) and websites (Next.js, Vite, Svelte). Database workloads primarily use MongoDB, PostgreSQL, and ClickHouse.
- PM2 is for legacy applications: restart support is required; a repository update command is a possible later addition whose scope and authorization still need definition.
- Git providers in scope: GitHub (GitHub App installations and personal access tokens), including private repositories, and self-hosted Forgejo/Gitea using access tokens. GitLab and Bitbucket are deferred. Both shared administrator-managed and personal connection ownership are supported.
- GitHub App onboarding uses a guided repository-selection workflow: select a connected GitHub App installation/account, select a repository available to that installation, then select its branch. No owner/repository typing is required in the normal flow. Show installation/account identity clearly when the same GitHub App has multiple installations.
- Also provide a first-class **Repository URL + personal access token** setup path that requires no GitHub App. This is required for projects in organizations where the user cannot install an App. Accept a canonical HTTPS GitHub repository URL, a newly entered PAT or an authorized saved PAT connection, validate repository read access, then select a branch and configure deployment normally. A direct URL must work without repository-listing permission. Store the token encrypted in the connection, never in the URL, revision, or logs. Organization approval/SSO restrictions may still apply to a PAT; show actual access failures without suggesting that PATs bypass organization policy.
- Source builds require a committed Dockerfile. Existing prebuilt-image and image-only Compose deployment modes remain supported without requiring a Dockerfile. Offer an editable repository-based Dockerfile suggestion for the user to copy or commit. Never silently commit it or deploy a dashboard-only Dockerfile override. Prioritize npm/pnpm Node applications, especially pnpm Next.js.
- Monorepos require explicit application root, Dockerfile path, and Docker build context settings. These settings are distinct: a website in a subdirectory may still need a repository-root build context for workspace dependencies.
- Deploy pushes to the configured branch by default after deployment setup is completed. Provide a per-app automatic-deployment toggle. Never deploy merely because a user browses a repository or edits a suggestion.
- First-release placement: one selected server per app. Multi-server copies and cluster orchestration are later work.
- Deployment policy: blue/green targeting near-zero downtime by default. Start and verify the replacement before shutting down/deleting the old version. Preserving existing requests, WebSockets, or SSE connections is not required. Stop-before-start deployment requires an explicit per-app setting; never silently fall back to it.
- Compose rollouts target selected web/API services. Keep databases and shared dependencies running unless a Compose change requires restarting them. Anyone authorized to deploy the app may trigger those required restarts, including through automatic deployments; no separate admin approval is required. Support per-service watch paths and a configured redeploy/restart action. Near-zero downtime applies to replaceable web/API services; required dependency restarts may interrupt the app.
- Watch paths use repository-relative globs. All files trigger until rules are configured; a shared path may trigger multiple services; manual deployment can override filters. Include deletions/renames and changes since the last successfully deployed revision of each service when determining affected services, so a failed earlier deployment does not lose a required update.
- Deployment queue: FIFO by authenticated webhook receipt order, scoped to the app. Finish the active run, then process the next queued push at its exact commit. Do not reorder, collapse, or automatically cancel older pending commits, and do not fall back to older revisions on failure. Provider redeliveries remain deduplicated. Pause dispatch for the app when the serving version is uncertain until reconciliation establishes its state.
- Repository connections support both shared administrator-managed connections and personal connections. Credential ownership does not replace app deployment permissions; app users must never receive raw connection credentials.
- First release includes Git integrations, committed-Dockerfile suggestions, monorepo/watch-path settings, single-host blue/green, normal/developer variable editors, and managed PostgreSQL creation/import/backup/restore. Templates, automatic buildpacks, MongoDB/ClickHouse management, previews/environments, and multi-server deployments remain deferred.
- Readiness supports both configurable HTTP probes and Docker health checks. Blue/green requires at least one check, all configured checks must pass, and the default readiness timeout is 120 seconds (configurable). A readiness failure leaves the old version active.
- Migrations remain app-managed or manual in the first release; no dedicated pre/post-deploy or migration hooks. App-owned startup migrations are not made reversible by blue/green and must remain compatible with the serving version.
- Private npm packages and private container registries are in first-release scope, including build credentials for private base images. Separate build secrets from runtime variables; do not pass credential values through ordinary Docker build arguments or bake them into suggested Dockerfiles. Use BuildKit secret mounts and isolated registry authentication.
- Domain setup includes the domain, target Compose service/container port, managed NGINX routing, and HTTP-01 HTTPS. Offer optional Cloudflare DNS record creation through an authorized existing connection; manual DNS remains supported. Automatic DNS does not include DNS-01 or wildcard certificates.
- Each server/connector reports its detected public IPv4 and IPv6 (when available). Show those addresses in server details and prefill domain/DNS setup from the selected deployment server. Administrators may override the DNS target for NAT, load balancers, or proxies; manual address entry is a fallback, not the normal setup requirement.
- Long-term target: completely replace the existing platform on the currently externally managed server. PostgreSQL backup/restore and environment-variable editing in both normal forms and developer text mode are confirmed first-release requirements. Recreate databases in Kloud and import existing PostgreSQL exports into new databases; in-place adoption of the existing platform databases and overwrite restores are not required. Do not retire the existing platform before replacement workflows and data recovery are verified.
- PostgreSQL backups support disk, S3, or both per policy, with independently tracked destination outcomes and retention. Support daily/weekly/monthly presets and custom cron. Minimum retained restore points take precedence over storage caps: report the conflict and fail a backup when space is insufficient rather than delete protected points. the existing platform single-database `.dmp` custom archives are the required migration input; determine actual database/dump versions from the archive during import.
- Developer variable mode edits the complete `.env` set. Review added/changed/removed keys before saving; removed keys are deleted on confirmation. Normal mode provides per-variable controls over the same underlying draft.
- Secret reveal requires a separate app-specific grant; ordinary app management does not imply reveal. The full developer editor requires that grant. Normal masked editing remains available under existing configuration permissions.
- the existing platform proxy cutover may use a planned brief interruption to release ports 80/443 and start Kloud's proxy. Same-host integration with the existing platform's proxy is not a first-release requirement. Preserve a reversible cutover runbook.
- No inter-server VPN exists today. Help set it up separately, then let Kloud use the configured private addresses and report connectivity. Kloud-managed VPN enrollment/access administration is later work. Actual five-host installation/configuration is a separate execution task, not already performed by this plan.
- First release includes optional generic per-service public TCP and UDP forwarding, including TCP database access. App managers may enable listeners for their assigned services with source-IP allowlists; public database access requires TLS. Use same-host listeners initially, rather than adding a central cross-host gateway. PostgreSQL uses TCP; UDP is for other services. Public forwarding is optional and independent of VPN enrollment and HTTP domain routing.

## Revised deployment release plan

### Milestone A: connect repositories and configure reproducible builds

1. Add reusable encrypted shared and personal Git provider connections and repository/branch selection for GitHub and self-hosted Forgejo/Gitea, including private repository access. Support GitHub Apps and personal access tokens, plus Forgejo/Gitea tokens. Administrators control shared connections; assigned-app users may use only repositories/connections explicitly delegated to them, or their authorized personal connections. Apply the ownership/revocation defaults below.
   GitHub App UX: connection/installation picker → searchable repository picker → branch picker → app/build settings. Fetch the installation's accessible repositories through GitHub's API using server-side credentials, handle pagination, and filter results by Kloud connection/repository delegation before returning them to the browser. Store provider repository/installation IDs plus the canonical name, rather than relying on typed owner/name strings. Refresh available repositories when installation access changes and provide actionable empty/revoked-access states. Existing manual repository configurations remain compatible; manual entry is not the default onboarding path.
   PAT UX: explicitly choose Repository URL + PAT → enter URL and token (or choose an authorized saved PAT) → validate repository access → branch picker → app/build settings. No App registration, installation, or installation-repository listing is required. Fetch canonical repository identity server-side and apply Kloud access checks; repository access alone does not grant app deployment permission. Display auto-deploy webhook status separately: provision a signed webhook when the PAT has permission, otherwise show manual webhook instructions. If neither token nor user can configure the repository webhook, manual deployments remain available and auto-deploy is shown as unavailable; polling is not implicitly added.
2. Add app root, build context, and Dockerfile path configuration with safe repository-relative validation. Detect package manager/workspace/framework evidence and explain the detected inputs. Never infer that a pnpm repository must be Next.js.
3. Produce an editable Dockerfile suggestion using repository evidence. Show where the file should be committed and how context/path settings relate to it. If the chosen commit lacks the configured Dockerfile, block deployment with a clear explanation.
4. Provision or guide signed push webhook setup for each provider. Verify repository and configured branch, deduplicate deliveries, and build the exact commit in app-level FIFO receipt order. Enable automatic deployment by default only when setup is completed and the app is deployable.
5. Reuse isolated builds, encrypted revisions, existing permissions, and retained artifacts. Support private npm packages and container registries (private base images, Compose image pulls, and image-service pulls). Provide encrypted scoped registry connections and build secrets through BuildKit secret mounts/isolated registry authentication; keep them separate from runtime environment values. Suggestions should demonstrate secret references rather than token literals. No dedicated migration hooks are included.

Acceptance: select a GitHub App installation, find a private repository through the searchable picker without typing its owner/name, select a branch, complete setup, and deploy a signed push automatically. Independently deploy a private organization repository using only its HTTPS URL and PAT, with no GitHub App or repository-listing prerequisite; exercise automatic webhook creation, manual webhook setup, and manual-only deployment when webhook management is unavailable. Verify pagination, multiple installations, filtered repository grants, token revocation, organization access errors, and removed installation access; manual entry must not bypass access checks. A private self-hosted Forgejo/Gitea app deploys from its configured branch; an npm app and pnpm Next.js monorepo build from committed Dockerfiles; private npm dependencies and a private base image build successfully; private Compose/runtime image pulls work; credentials are absent from build output, exported image files/history, and retained checkouts. Duplicate or wrong-branch webhooks do not create an extra deployment; queued pushes run FIFO; unauthorized teammates cannot use a connection or deploy an unassigned app. Suggestions never modify the repository automatically.

### Milestone B: blue/green release gate

1. Add a per-app deployment policy, defaulting to blue/green targeting near-zero downtime. Existing apps must receive an explicit compatibility review. Stop-before-start requires the per-app downtime setting.
2. Build first, start an isolated candidate while the old version serves, establish readiness using configurable HTTP probes and/or Docker health checks, switch the managed proxy, then stop/remove the old runtime while retaining rollback artifacts. Require at least one check and all configured checks to pass within the configurable 120-second timeout. Connection preservation/draining is not an acceptance requirement; use the technical defaults below for shutdown and probes.
3. Use stable app identities with separate release/container identities. Persist rollout stages so API/connector restarts can reconcile which release actually receives traffic.
4. Candidate startup/readiness failures must leave the previous version serving. Switch/reconciliation failures must produce a clear recoverable state and preserve the serving release. Never silently use the downtime path.
5. Add per-Compose-service watch path rules and actions (redeploy or restart), using the confirmed glob/default/manual-override rules. Replace only selected web/API services, keeping databases and shared dependencies running unless their configuration requires restart. App deployment authority includes required dependency restarts; show affected dependencies in the plan/history and never restart them merely because a web image changed. Compare resolved nonsecret service configuration and protected hashes of secret inputs to identify changed dependencies. Detect unsupported overlap conditions: fixed host ports, exclusive volume writers, singleton jobs, and incompatible schema changes. Block blue/green until compatibility is resolved or the app explicitly allows downtime. Do not duplicate an entire Compose stack containing databases as the default rollout strategy.
6. Keep blue/green on the chosen host; this milestone does not add multi-server routing or failover.

Acceptance: event ordering proves the replacement is ready before proxy cutover and before the old runtime is stopped/deleted; candidate failure leaves the old version serving; crash/reconnect at each rollout stage preserves or recovers a known serving version; stop-before-start is unavailable without the app setting. Probe both versions and exercise requests during cutover to detect an avoidable service availability gap. Existing requests/connections may terminate, so zero failed requests is not a release guarantee. Watch-path tests cover web-only changes, API-only changes, shared package changes, and unrelated changes, verifying exactly which services redeploy/restart. Unselected dependencies remain running except under the agreed required-restart policy.

### Milestone C: domain onboarding and first-release verification

1. Add domain setup to the deployment workflow: hostname, target service, internal port, network, and HTTPS setting. Reuse the current NGINX reconciliation and Certbot controller.
2. Extend connector inventory with detected public IPv4/IPv6, detection time, and detection status. Surface them in server details and prefill optional Cloudflare A/AAAA creation from the selected host's effective addresses (admin override, otherwise detected address). DNS writes require the existing DNS permission/delegation checks in addition to app deployment permission. When the user lacks DNS access, offer manual DNS instructions without granting extra authority.
3. Show the exact record before the user saves domain setup. Identical existing records are a no-op; conflicting records require an explicit authorized update, never a silent overwrite. Do not alter unrelated records or delete DNS merely because an app is removed.
4. Report DNS, route application, and certificate issuance as separate statuses. A DNS/ACME failure must not falsely report working HTTPS or disrupt an existing serving route. Let the user retry after fixing reachability; do not block unrelated builds while DNS propagates.
5. Finish provider, credential, FIFO, selective Compose rollout, restart recovery, access-control, and domain acceptance checks before declaring the release complete. Verify real public HTTP-01 issuance on an isolated reachable domain.

Acceptance: IPv4-only and dual-stack connectors report their public addresses; detection failures do not break inventory or deployments; older connectors remain compatible. Domain setup prefills the selected server's effective addresses and honors an admin override. An authorized user attaches a domain and creates its Cloudflare record; an app deployer without DNS permission receives manual instructions; conflicting DNS is preserved unless explicitly updated; HTTP traffic reaches the selected service and HTTPS becomes ready only after issuance. Both the manual-DNS and automatic-DNS paths work. An address change is visible without silently rewriting existing DNS.

### Milestone D: normal and developer variable editors

1. Add a normal key/value editor and a developer `.env` text editor over one versioned encrypted configuration draft. Switching modes must preserve values; saving either mode must not deploy or restart implicitly.
2. Parse developer text without shell execution or variable expansion. Support comments, blank lines, quoted values, literal dollar signs, empty values, and multiline values with a documented grammar. Reject invalid/duplicate keys with line-specific errors; do not save a partial parse.
3. Treat the submitted developer document as a full replacement. Show a review of added/changed/removed keys, mask secret values in the review, and delete omitted keys only on confirmed save. Preserve build/runtime metadata for retained keys unless explicitly edited. Detect stale revisions before applying the edit.
4. Define secret reading separately from configuration update: existing write-only masked revisions must not be serialized into an apparently complete `.env` document containing placeholder values. Add explicit app-scoped secret-reveal authority, with administrator access and explicit delegation for teammates. Loading/copying complete plaintext requires that authority; without it, use masked per-variable editing that preserves unchanged secrets and explain why full developer mode is unavailable.
5. Display which apps/services need redeployment after a configuration change. Keep shared variables, previews, and named environments deferred; both editors are useful without those features.

Acceptance: normal-to-developer-to-normal round trips preserve literal/multiline/empty values; a reviewed deletion actually removes the key; cancelling review changes nothing; invalid syntax and stale edits do not overwrite saved state; masked placeholders are never mistaken for real plaintext; unauthorized users cannot reveal variables through either mode or API output.

### Milestone E: PostgreSQL creation, import, backup, and restore

1. Add a project-scoped PostgreSQL resource on a selected connector, with pinned supported versions, generated encrypted credentials, persistent storage, private networking by default, health, connection details, logs, and lifecycle operations. Permissions distinguish database read/manage, backup execution, restore-to-new, destination administration, and credential reveal.
2. Create new databases under Kloud and import the existing platform PostgreSQL exports into them. Required first-release format: single-database `pg_dump --format=custom` archives restored using `pg_restore`; inspect the `PGDMP` signature and archive metadata, not the filename alone. The supplied `pg-dump-postgres-...dmp` name is consistent with this format, but the actual file must be validated before import. Validate client/server/dump compatibility, roles/ownership and required extensions before execution. Record import runs, redacted logs, progress, and terminal outcomes. Keep the source database untouched. SQL/gzip/tar and cluster-wide `pg_dumpall` imports are optional later extensions unless real export inspection establishes they are needed.
3. Add disk backup destinations rooted in administrator-configured directories on the selected host, plus encrypted S3-compatible destinations with connection tests. Each policy selects disk, S3, or both; track artifacts, size, checksum, source/version metadata, completion, and retention independently per destination. For both destinations, a failed S3 upload must not invalidate/delete a completed disk backup or count as a completed S3 restore point. Show a partial-success outcome. For S3-only, local staging is temporary and excluded from retained disk points; clean it after confirmed upload, and report upload failures without claiming a remote backup. A local path alone is not a cross-server restore mechanism.
4. Add on-demand backups and daily/weekly/monthly/custom-cron policies with an explicit timezone, next-run preview, and durable job leases/history. Use logical PostgreSQL dumps and suitable versioned clients. Scheduled database backups are included; arbitrary scheduled shell jobs remain deferred.
5. Add configurable storage-space limits and minimum retained restore points per policy/destination. Prune oldest complete eligible artifacts while preserving the configured minimum; failed/partial artifacts do not count as restore points. The minimum wins over the cap: surface a conflict and fail/stop a backup safely if space is insufficient, never remove a protected point to force compliance. A new artifact becomes complete only after verification; interrupted writes cannot replace a protected point. Account for temporary dump/upload space and a free-space reserve. Serialize backup/prune operations and show destination-specific conflicts; operate only on artifacts owned by the selected policy. Neither policy caps nor retention authorize deleting unrelated server/S3 files.
6. Restore a selected backup into a newly named database, never overwrite an existing target in this release. Offer disk/S3 source selection and imported existing PostgreSQL exports. Verify target prerequisites and integrity, isolate partial restores, and retain source artifacts on failure. Switching application connection strings is a separate explicit configuration change.
7. Reuse durable connector execution, idempotency, and outcome reporting for database jobs. A disconnect during a database operation produces an unknown/reconciling state rather than an automatic duplicate restore. Backup/restore lifecycle and failures must be visible in the dashboard; external notification channels remain separate backlog work.

Acceptance: create PostgreSQL, import a representative real existing PostgreSQL export, and verify schema/data; generate scheduled and on-demand backups to the agreed destinations; restore each supported format/source into a new database and verify known data. Source database and existing targets remain unchanged. Exercise retention boundaries, storage exhaustion, partial uploads, lost connectors, incorrect credentials, timezones, and unauthorized access. Deleting an app must not implicitly delete its database or restore artifacts.

### Milestone F: private connectivity and public TCP/UDP forwarding

1. Document a separate VPN setup workflow for the five servers, and record each connector's private/VPN addresses independently from public DNS addresses. Verify host-to-host and app-container-to-database connectivity; a host VPN ping alone is not sufficient. Keep database access private by default, with bindings/firewall rules scoped to the intended private interface and project-authorized clients. Do not rely on a Docker bridge spanning hosts.
2. Add optional service-owned TCP/UDP listener configuration: protocol, same-host public bind address/port, target service/internal port, source IPv4/IPv6 CIDR allowlists, enabled state, and desired/applied/error status. Support TCP and UDP on the same numeric port as distinct listeners; detect actual address/protocol/port conflicts, including existing host services. The initial model is host-local forwarding, not a central gateway or cross-host routing feature.
3. App managers may create/update/disable listeners only for assigned apps/services; administrators own host bindings, protected/reserved ports, and any exceptional policy. Reserve management/SSH/VPN and HTTP proxy ports from ordinary listener assignment. Listeners default disabled. Source-IP allowlists are optional: an empty list means allow anyone on the configured listener/address families; a nonempty list permits only matching source CIDRs. Label the empty state "Allow anyone" in settings and summaries. Invalid entries must fail validation rather than being discarded into an empty allow-all list. Validate target ownership again at dispatch; reconcile removals/revocation and do not let a listener target arbitrary host/private-network destinations.
4. Enforce CIDR rules where the real source address is available, before translation/proxying can hide it. Reconcile protocol-aware host firewall and forwarding/proxy configuration without replacing unrelated host/VPN/SSH rules. Do not assume Docker port publication inherits host firewall protections. Verify permitted and denied traffic through real external test clients for IPv4 and IPv6 where configured.
5. Public PostgreSQL listeners must require native PostgreSQL TLS, with a valid hostname/certificate and client instructions using hostname verification. Raw TCP pass-through does not itself add encryption; do not treat the HTTP proxy certificate as sufficient or use a generic TLS terminator without PostgreSQL protocol support. Provision/renew database certificates and configure public access to reject plaintext, or block enabling that public listener until those prerequisites are satisfied. Keep credentials required. An encrypted VPN and database TLS are separate controls.
6. Keep raw listener state stable across target-container replacement where supported, resolving the currently applied service release. Report backend/proxy failures and remove obsolete owned rules. Existing TCP/UDP sessions may end during replacement; do not extend the HTTP near-zero-downtime promise to arbitrary raw protocols. Stateful PostgreSQL restarts do not gain blue/green semantics from forwarding.

Acceptance: app managers configure TCP and UDP only for assigned services; empty allowlists admit any source, nonempty lists admit matching sources and reject others, and removal disables access. Verify transitions between empty and restricted lists, invalid CIDR rejection, conflicting ports, IPv4/IPv6 CIDRs, connector restart reconciliation, protected host services, and source-IP enforcement under Docker networking. Public PostgreSQL rejects plaintext and supports verified TLS after certificate renewal regardless of allowlist contents. Across the separately established VPN, an app container on another server connects to the intended private PostgreSQL endpoint without opening the public listener. Public address discovery never overwrites the private address configuration.

### Technical defaults for implementation

These are proposed engineering defaults, not additional user decisions. They make the plan executable and can be adjusted during implementation if repository constraints require it; material behavior changes must be surfaced.

- **Repository paths:** store app root, Dockerfile path, and build context separately as repository-relative POSIX paths. Resolve Dockerfile paths from repository root and show the resolved values together. Validate containment, including symlinks. Detect suggestions from the selected app root and root workspace/lockfile metadata. Honor the committed Dockerfile for non-Node apps; Node-specific suggestions must not limit Go or other Dockerfile builds.
- **Watch rules:** use case-sensitive POSIX glob matching with `**`, `*`, `?`, and explicit include/exclude lists; exclude wins. Missing includes mean all paths. Compare each target service's last successfully applied commit to the queued commit, including both names of renames and deleted paths. With no baseline, unavailable history, or a force-push without a safe comparison, treat all paths as changed. Changes to selected deployment definition files trigger replanning even if application source filters do not match. Record no-op pushes as skipped. Manual deployment chooses targets and may bypass filters, while joining the same FIFO queue.
- **Redeploy versus restart:** redeploy builds/pulls the selected commit's artifacts and replaces the service; restart restarts the current runtime without rebuilding or updating its source. Mark restart actions as potentially interrupting service. For selected web/API services, require the app's downtime setting for in-place restart; dependency restarts use the separately confirmed automatic authorization rule. This distinction prevents a restart rule from silently bypassing blue/green policy.
- **Queue failures:** after a known failed build/readiness check with the serving release established, record failure and continue FIFO. Unknown execution/cutover state pauses that app's dispatch until reconciliation; never retry an ambiguous command blindly. Receipt sequence, not Git commit timestamp, determines ordering. Retain existing connector-level serialization initially; app-level FIFO does not promise concurrent deployment across the same host.
- **Queued configuration:** bind each accepted push/manual deployment to its exact commit and an immutable encrypted deployment-configuration revision at enqueue time. Later path, environment, route, or policy edits do not silently rewrite queued runs. Credential revocation and current permissions are still enforced at dispatch. Display the bound revision in history and allow explicit cancellation of obsolete pending runs; do not automatically collapse the FIFO queue.
- **Readiness:** default HTTP GET probe every 2 seconds, 5-second per-request timeout, HTTP 200-299 success, against the candidate's internal port/path (default `/`). All configured checks must pass in the same evaluation before cutover. Docker checks require `healthy`; missing/unhealthy checks do not count as ready. Begin the default 120-second readiness window after candidate startup. Persist probe failures in redacted run output. Treat these values as configurable.
- **Shutdown:** after confirmed proxy cutover, honor Compose `stop_grace_period` where provided, otherwise default to 10 seconds. Existing connections may close. Retain image/configuration artifacts for explicit rollback, rather than requiring the old container to remain running indefinitely.
- **Compose identity:** preserve shared dependency names, networks, volumes, and aliases; give web/API candidates release-specific identities. Switch all managed routes for the selected service before retiring the old version. Do not attach both releases to an ambiguous shared routing alias. Cross-app dependencies are not automatically restartable based on one app's permission. Fixed ports, exclusive writers, and app-internal service discovery need compatibility checks.
- **Connections:** personal credential values remain visible only as masked metadata to others; they may power a persistent app binding authorized by their owner without sharing raw credentials. Owner disablement, removal from the relevant project, connection revocation, or lost delegation blocks subsequent claims until an authorized connection is selected. Keep the serving app running. Do not silently convert personal credentials into a shared connection. Recheck authorization at dispatch and before returning results.
- **Webhooks:** prefer automatic provisioning when credentials have sufficient permission; otherwise provide URL, signing-secret setup, and connection validation instructions. Display connectivity failures clearly for private Forgejo/Gitea instances. Enrollment does not require access to the database or host socket from Git providers.
- **Secrets:** separate source checkout credentials, registry credentials, build secrets, and runtime environment values. Scope resolution to the app and connection owner/delegation. Suggested Dockerfiles show BuildKit secret references for private npm configuration and remove temporary configuration before layer completion. Credential-isolation acceptance checks use controlled test repositories; arbitrary user Dockerfiles can still deliberately print secrets and remain trusted deployment inputs.
- **Build inputs:** explicitly configure nonsecret build arguments separately from BuildKit secrets and runtime variables. This is necessary for build-time framework values such as Next.js `NEXT_PUBLIC_*` and Vite `VITE_*`; public bundle inputs are not private secrets. Rebuilding is required to change baked-in values. The committed Dockerfile must declare/use the corresponding arguments or secret mounts; the dashboard does not rewrite it. Per-variable build/runtime metadata must round-trip through the normal/developer editors without exposing build-secret values as ordinary arguments.
- **Public address discovery:** connector-side detection runs at startup and periodically (proposed default: every 15 minutes) using bounded, configurable HTTPS public-address discovery requests for IPv4 and IPv6 independently. Validate global unicast addresses and do not infer public addresses from the API WebSocket peer, private interfaces, or container bridge addresses. Report last successful values/time and current detection errors separately; missing IPv6 is valid. Detection failure must not block ordinary inventory collection. An outbound public address is a suggested ingress target, not proof of inbound reachability; retain an admin override and show stale/unknown status. Expose addresses only within existing server/app access scopes, not an unauthenticated endpoint.
- **DNS:** use existing delegated Cloudflare credentials and prefill from the selected connector's detected public addresses, with admin-configured DNS targets taking precedence. Show A and AAAA independently; do not automatically publish an unverified IPv6 route merely because IPv6 egress detection succeeds. Unknown/stale addresses require review or manual entry. Address changes update server metadata and show affected domain targets for review; automatic ongoing DNS synchronization is outside this release. Keep the automated path compatible with the existing HTTP-01 proxy; wildcard/DNS-01 work stays deferred.
- **PostgreSQL archives:** use custom-format dumps for Kloud's own single-database backups, and store source server/dump-client versions in the manifest. Inspect imported archives with a compatible `pg_restore --list` client and record source/dump version metadata when available. Validate target compatibility and extensions before import; do not infer a PostgreSQL major version from `postgres` in the filename. Default new-target restore to remapping ownership to the selected target role (`--no-owner --no-acl`); preserving original ownership/ACLs requires explicit role mapping and preflight. A representative actual the existing platform archive must pass restoration before the migration release is accepted.
- **Retention starting configuration:** exact storage budgets/minimum counts were not supplied. Require explicit values in backup-policy setup instead of inventing a global disk/S3 budget; provide editable suggestions only. No policy activates without showing its effective destinations, timezone, storage limits, minimum points, and next run. Logical backups and restore-to-new are included; PITR/WAL archival is outside this release.

### Migration and deployment ownership

The user has confirmed complete eventual replacement of the existing platform on this server. PostgreSQL backups/restores and normal/developer variable editing are now first-release requirements. Recreate databases in Kloud and import existing PostgreSQL exports into new targets; use a planned brief interruption for proxy cutover. The production cutover date remains undecided. Do not implicitly deploy a second proxy onto its ports 80/443 or replace externally managed containers.

- A connector may discover existing containers for inventory under current permissions; discovery alone must not claim deployment ownership.
- Read-only monitoring and selected-app cutover can be transitional stages toward complete replacement; an automatic importer or live-volume migration tool has not been requested.
- The planned cutover releases 80/443 from the existing platform before Kloud NGINX binds them. Inventory may coexist beforehand; independent competing public proxies may not. External-proxy integration is not required for this migration.
- Before takeover, map repository/branch, Dockerfile/context/Compose, image references, variables/secrets, volumes, networks, domains, restart policy, and deployment triggers. Retain stable data volume identity and disable the old deployment trigger before enabling the new owner.
- A route/certificate/data cutover needs a rollback procedure. Do not assume near-zero app replacement also guarantees zero-interruption migration between control planes or database engines.
