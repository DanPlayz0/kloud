# Application releases

New application drafts default to blue/green. Older drafts without a deployment policy require an explicit compatibility review; they never acquire stop-before-start behavior implicitly. Deployment workers must advertise `rollout-v1`; an older inventory-only/deployment connector cannot claim these jobs. Moving an established app to another host requires a separate migration/cutover workflow and is blocked by this release controller.

## Readiness and switching

For single-container applications, the connector creates a release-specific candidate while the old container remains running. Candidate network aliases contain only the release identity. Docker health and HTTP checks can be combined; every configured check must pass in the same evaluation. Defaults are a 120-second window after startup, a two-second evaluation interval, HTTP GET `/`, a five-second request timeout, and HTTP 200–299 success. HTTP requests run in an isolated helper container sharing only the candidate's network namespace; they do not follow redirects or receive connector/provider credentials. The configured build-helper image must be available for HTTP probing.

A candidate startup/readiness failure removes only the candidate and preserves the old serving version. Once readiness passes, the API changes the app's managed NGINX targets transactionally. The connector waits until the proxy reports that exact route revision applied before stopping and removing the old runtime. Existing requests, WebSockets, and SSE streams may end at switch; connection draining is not guaranteed. Compose service `stop_grace_period` is honored where provided; otherwise the configured default is ten seconds. Old image/configuration artifacts remain available for explicit rollback, which never restores volume/database contents.

Initial deployment can run without a domain. Attach a managed domain to the reported release container before replacing it through blue/green. Replacements require an owned managed route, so the controller cannot falsely claim that an arbitrary published port was switched.

Fixed host ports, shared host/container namespaces, fixed addresses, unreviewed overlap, and writable candidate volumes fail closed. Review singleton jobs and app-owned startup migrations explicitly. The dashboard cannot prove schema compatibility from a Dockerfile. Stop-before-start requires the app's explicit downtime setting; it is not a fallback.

## Selected Compose services

Enable selective Compose settings and name the replaceable web/API services exactly as they appear in the resolved Compose definition. Each service has include/exclude watch paths, a redeploy or restart action, and an optional HTTP-probe override. Docker readiness still applies when configured. The selected services' candidates become unique Compose service keys and container names, avoiding Compose's automatic shared service-name DNS alias. They join the existing stable networks. The database/shared dependency stack is not cloned.

All selected candidates become ready as a rollout unit before the API changes their matching managed routes in one transaction. Unselected routes remain unchanged. Each replaced existing service needs a managed route; internal-only service discovery that still relies on a stable `web`/`api` alias must be resolved before using this mode. Dependencies between selected candidates, shared discovery links, fixed ports/namespaces/addresses, replicas, and writable candidate mounts are currently rejected. In particular, do not claim support for a multi-service stack whose internal dependencies have not passed these isolation checks.

Unselected services remain in the stable Compose project. Their resolved configuration, secret inputs, and actual image IDs are compared using connector-keyed HMACs; a changed dependency is applied using the existing project's service-scoped Compose update. A web image change alone does not restart an unchanged dependency. Required dependency updates can interrupt the app and are included in the redacted execution plan/log. Their before/after stages are durable, and successful dependency hashes are retained even if a later web candidate fails. An interrupted dependency update remains paused for operator inspection rather than being blindly replayed. The deployer's app permission authorizes these required dependency updates. Source image pulls use the app's isolated registry configuration, which is removed after execution.

`restart` operates on the currently running service without rebuilding/updating its source and requires explicit app downtime permission. It does not advance that service's successfully deployed source baseline. Stop-first selective replacement also requires explicit downtime permission and does not inherit the HTTP near-zero-downtime guarantee.

Watch paths are case-sensitive repository-relative POSIX globs supporting `**`, `*`, and `?`. Empty includes mean all paths; exclude wins. A changed deployment-definition file forces replanning. Deletions and both names of a rename count. Each service compares the queued commit against its own last successfully applied source commit, so failed releases do not lose updates. Missing history, a nonancestor baseline, bounded-history truncation, or absent checkout metadata conservatively means all paths changed. Manual deployments bypass filters. No matching service produces a `skipped` history entry.

## Durable queue and reconciliation

Receipt sequence, shared across legacy/source deployment queues, determines FIFO order. Runs bind their exact commit and encrypted revision at enqueue time. Changing configuration or disabling future automatic deployment does not cancel accepted work. Queued cancellation is explicit via the app's queue controls. Provider delivery IDs remain deduplicated.

The API stores prepared/start/readiness/cutover/serving/retirement stages and stable app release state. The worker maintains a ten-second execution heartbeat, aborts on lease loss, and emits progress during readiness and cutover. Reconciliation waits for a ninety-second stale lease. A lost worker with a recorded rollout is claimed for reconciliation after its progress lease goes stale, rather than running the deployment again. It inspects owned candidate/prior containers, rechecks candidate readiness, confirms the proxy's applied revision, and finishes retirement or restores verified prior routes. Unknown cutover outcomes preserve both runtime sets and pause that app. An interruption before a recorded rollout requires operator inspection; it is never retried blindly. Other apps remain independent, subject to existing connector-level execution serialization.

`GET /projects/:project/services/:service/queue` reports serving identity, pause reason, receipt order, and rollout stage. `POST .../runs/:id/cancel` cancels only a pending run. Mutations require current deployment permission. At dispatch, the API rechecks the active requester, app deployment permission, credential-owner membership, connection delegation, and revocation. Credential revocation blocks later claims while leaving the serving app running. Dispatch secrets are encrypted separately so final logs can still be redacted after a credential is removed.

Compose runtime identity is stored as `service_release_state.compose_state.targets`, keyed by Compose service. The top-level `serving` value identifies the rollout unit and is not itself a Compose backend container. Routing/forwarding integrations must resolve the selected service through that map.

## Verification boundary

Automated tests cover replacement-before-retirement ordering, candidate failure, ambiguous cutover preservation, all-configured readiness, protected overlap rejection, watch matching, selected-only Compose models, dependency HMAC comparison, durable API transitions, actor access, and FIFO receipt ordering. PostgreSQL integration tests use isolated schemas.

Production acceptance additionally requires representative host tests with real managed NGINX traffic during single/multi-service switches, process/API/connector interruption at every stage, private registry pulls, Compose dependency restart behavior, and representative app-internal discovery. Public HTTP-01 issuance requires an isolated reachable domain. Unit tests and simulated proxy acknowledgements are not evidence that those host/public-internet acceptance checks have passed. Do not retire the existing platform or advertise an accepted zero-interruption guarantee based only on these tests.
